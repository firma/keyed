Harness Engineering 标准设计：下一代 AI Agent 产品为什么会长成一套运行时系统

By keyed

发表于 2026-04-02

在过去两年，AI 产品行业有一种很常见的误判：很多人把“模型能力提升”直接等同于“产品能力提升”。

于是我们看到大量产品讨论都集中在模型层：谁的 benchmark 更高、谁的上下文更长、谁的价格更低、谁的推理更强。

但当 AI 真正进入工作流、进入终端、进入仓库、进入团队协作之后，问题开始完全不一样。

企业和开发者真正关心的，已经不是“模型回答得聪不聪明”，而是：

  • 它能不能稳定地完成一个复杂任务
  • 它能不能在权限边界内行动
  • 它能不能在长上下文里不失真
  • 它出错之后能不能恢复
  • 它能不能被团队制度化部署
  • 它能不能和其他代理、工具、人类一起协作

这时，真正决定产品形态的，就不是模型本身，而是 Harness Engineering。

导读

所谓 Harness Engineering，并不是一个时髦的新名词，它更像是 AI Agent 时代的软件工程必修课。

它讨论的不是“模型会不会”，而是“模型被接入真实世界之后，系统应该如何把它约束成一个可靠执行体”。

如果说大模型提供的是认知能力，那么 Harness 提供的就是：

  • 控制能力
  • 执行能力
  • 边界能力
  • 恢复能力
  • 协作能力
  • 制度化能力

也正因为如此，未来真正领先的 AI Agent 产品，大概率不会只是一个聊天框，也不会只是一个 IDE 插件，而会是一整套可编排、可审计、可恢复、可协作的运行时系统。

核心要点

  • Harness Engineering 的核心任务，是把不稳定的模型输出约束进稳定的工程系统。
  • 标准化设计至少应覆盖六层：控制平面、查询循环、工具与权限、上下文治理、错误恢复、多代理与验证。
  • 对企业和开发者而言，真正可用的 AI Agent 产品，价值核心是“可控自治”，而不是单次演示中的惊艳效果。
  • 未来 AI 工具行业的竞争，将越来越像运行时平台竞争，而不是单纯模型能力竞争。
  • 开发者工具、终端 Agent、工作流自动化，将是 Harness Engineering 最先成熟的三个商业场景。

什么是 Harness Engineering

可以把 Harness 理解为 AI Agent 的“运行时骨架”。

模型本身像大脑，但没有骨架、神经、约束和反射系统，大脑并不能直接变成一个可靠的行动者。

Harness 负责回答以下问题：

  • 模型何时推理，何时行动
  • 它能调用哪些工具
  • 哪些动作要审批，哪些动作可直接执行
  • 它的记忆如何组织，如何避免污染
  • 会话如何持久化，如何恢复
  • 多个代理之间如何分工与验证
  • 团队如何把这些规则沉淀成长期制度

所以 Harness Engineering 的本质，不是做一个更酷的 AI，而是做一个不会轻易失控的 AI 系统。

一套标准设计，应至少包含六层架构

一、控制平面：Prompt 是系统政策层

很多人对 Prompt 的理解还停留在“告诉模型怎么说话”。

但在成熟 Agent 系统里，Prompt 的作用更接近控制平面：它定义系统边界，而不是人格表演。

一个标准控制平面通常应包含：

  • 角色与任务边界
  • 工具调用规则
  • 风险升级路径
  • 预算与成本限制
  • 输出风格与交付标准
  • 记忆写入约束
  • 用户确认与中断条件
  • 子代理调用原则

Prompt 不是装饰层，而是控制策略入口。

二、查询循环：让 Agent 真正“持续工作”

Agent 和 Chatbot 的本质差别，在于循环。

一个聊天机器人大多是一轮输入、一轮输出；一个 Agent 则必须不断重复：

理解任务 → 形成计划 → 调用工具 → 读取结果 → 更新状态 → 决定下一步

这个循环就是 Query Loop。它是整个系统的心跳。

好的 Query Loop 要解决四个关键问题：

  1. 状态推进：任务如何逐步接近完成，而不是反复空转。
  2. 决策切换：什么时候该继续推理，什么时候该执行工具。
  3. 异常管理：工具失败、权限被拒、上下文不足时怎么办。
  4. 停止条件：什么时候应该结束，而不是无穷循环。

没有可靠 Query Loop，就没有真正的 Agent。

三、工具与权限：把行动能力装进笼子里

AI Agent 一旦能读文件、改代码、跑命令、调接口，它就不再只是“生成内容”，而是在执行现实动作。

这意味着权限治理必须前置，而不能事后补洞。

一套标准设计通常包括：

  • 工具清单与能力边界
  • 路径级或参数级权限判断
  • allow / ask / deny 三段式策略
  • 人工审批中断点
  • 沙箱、隔离目录或受限执行环境
  • 审计日志与调用记录
  • 高风险命令黑名单与模式识别

这层设计的核心原则是：

Agent 可以有行动能力，但不能默认拥有无限行动权。

四、上下文治理：Memory 是预算制度，不是仓库

大模型上下文窗口再长，也不意味着“把一切都喂进去”是正确策略。

真正成熟的系统，会把记忆治理当成一种预算制度，而不是堆积制度。

比较理想的结构通常是：

  • 常驻索引层：保留当前最重要的事实、文件位置、任务状态
  • 主题知识层：分门别类记录项目结构、偏好、规则、历史决策
  • 原始观察层：保留日志与工具结果，但按需检索，不整段常驻

这能解决三个长期难题：

  1. 上下文膨胀
  2. 错误信息反复污染后续推理
  3. 成本和延迟失控

Memory 设计得好，Agent 才能在长任务中保持清醒。

五、错误恢复：生产系统必须允许失败

几乎所有 AI Agent 产品的早期原型，都有一个共同问题：一旦某一步出错，整个任务就碎了。

但真实工作流不是这样。真实世界中，失败、打断、误判、超时、审批取消，都是常态。

因此标准设计必须内建恢复能力：

  • 文件写入失败后可重试或回滚
  • 批处理任务可从上次检查点继续
  • 工具异常不会直接让整轮状态失真
  • 会话可持久化并恢复上下文
  • 不确定信息可被标记和复核

错误恢复不是附加模块，而是生产级 Agent 的基础设施。

六、多代理与验证：把复杂度拆开，把风险分散

随着任务复杂度上升，单代理模式会越来越吃力。因为它既要理解任务、又要操作工具、又要校验结果、又要维护上下文，最终非常容易在高压下失真。

多代理架构的价值就在这里：

  • 主代理负责规划与汇总
  • 执行代理处理具体子任务
  • 验证代理负责复核关键结论
  • 研究代理负责信息检索与证据整理
  • 代理之间通过明确协议协作，而不是共享一锅混乱上下文

这会把模型不稳定性从“单点灾难”变成“局部可控风险”。

Harness Engineering 为什么会成为行业分水岭

我认为接下来 AI 工具行业会出现一个很明显的分层。

第一层：模型接入型产品

这类产品主要是把模型包一层 UI 或工作流，短期能跑得很快，也容易做出 demo，但稳定性和可扩展性通常有限。

第二层：工具增强型产品

它们开始加入文件、终端、搜索、数据库、自动化流程，产品能力明显增强，但如果没有严格 runtime 设计，仍然容易在复杂任务下失控。

第三层：运行时系统型产品

这类产品的重点已经不是“接入什么模型”，而是“如何组织模型、工具、权限、记忆、恢复与多代理”。

我认为，真正能穿越未来两三年竞争周期的，大概率会是第三层。

原因很简单：模型能力会扩散，界面设计会被模仿，但运行时工程能力的复制成本最高，且最贴近真实生产场景。

前沿 AI 工具行业，未来会往哪里走

结合当前趋势，我对这个行业的判断是这样的。

1. 开发者工具会继续跑在最前面

因为代码、终端、Git、测试、CI/CD 这些环境天然结构化、可验证、可回滚，非常适合 Agent 深入接管。所以 AI 编程与工程自动化，会继续是 Harness Engineering 最快商业化的领域。

2. 企业买单的核心会从“更聪明”转向“更可控”

企业不是为了体验惊艳买单，而是为了降低成本、提升效率、控制风险买单。谁能把权限、审计、恢复、隔离、多代理编排做扎实，谁更容易真正进入组织级采购。

3. 工具协议与运行时标准会变得越来越重要

未来行业会越来越依赖统一的工具接入协议、消息协议、记忆层结构、审批流程、会话恢复机制。因为没有标准，系统很难规模化，也很难跨团队复用。

4. 多代理将从“实验特性”变成“默认能力”

今天很多团队还把多代理当作炫技功能，但未来它会成为高复杂任务的默认架构。尤其是在研究、编码、验证、文档、运营自动化这些长链路任务中，多代理几乎不可避免。

5. AI 工具会越来越像“认知执行基础设施”

未来最强的 AI 工具，并不只是某个单点应用，而会成为组织内部的一层通用执行基础设施。它既连接模型，也连接系统、权限、知识库与业务流程。

谁做成这层基础设施，谁就不只是做了一个工具，而是定义了新的工作操作面。

结语

如果把过去两年的 AI 产品演进总结成一句话，大概是：

从“模型能做什么”，走向“系统允许模型怎样稳定地做事”。

这背后对应的，就是 Harness Engineering 的崛起。

它不是边角料，不是实现细节，也不是只属于少数底层工程师的话题。它会越来越成为 AI 产品负责人、技术架构师、开发者工具团队、企业自动化团队共同面对的主战场。

未来的顶级 AI Agent 产品，拼的不是谁更像人，而是谁更像一个可靠系统。

而一旦行业进入这个阶段，真正的赢家，往往不是最会讲故事的人，而是最会把模型装进制度与运行时的人。

今天的 AI 生态，正在把行业推向哪一个新阶段？

By keyed

发表于 2026-04-02

如果只看今天 AI 圈的表层新闻，你会觉得这依旧是一场熟悉的模型竞赛：有人发新模型、有人做新集成、有人降价格、有人继续推 Agent。

但如果站在行业金字塔顶端的视角往下看，今天的变化已经不是“哪家模型又强了一点”这么简单。更准确地说，AI 生态正在进入一个新的竞争阶段：从模型竞争，转向运行时竞争；从单点能力竞争，转向系统级交付竞争。

今天最值得看的几条信号，分别来自 OpenAI、Anthropic、Cursor 与 Apple 所代表的四个方向，而它们拼在一起，几乎已经把未来一段时间 AI 工具行业的主线写清楚了。

导读

站在更高维度看，今天 AI 行业最重要的，不是某一条单独新闻，而是这些新闻共同构成了一条非常明确的产业迁移路径：

  • OpenAI 正在把 Codex 从“模型能力”升级为“跨终端、IDE、云环境与代码审查的统一开发平台”
  • Anthropic 的 Claude Code 相关讨论，则持续把“Agent Harness”与“运行时工程”推到行业视野中心
  • Cursor 则试图通过更低成本、更长任务、更强产品内闭环，证明第三方 AI coding 平台仍有生存空间
  • Apple 在 Xcode 中更深地接入 AI Agent，并拥抱 MCP 这类开放协议，说明 agentic coding 正在从实验形态走向主流开发工作台

如果把这些线索合并，你会发现一个比“AI coding 很火”更重要的结论：

AI 生态今天真正发生的变化，是行业正在从“提供智能答案”，转向“提供可控执行系统”。

核心要点

  • 今天 AI 行业最强烈的趋势，不是模型单点升级，而是 Agent 化、运行时化与平台化。
  • OpenAI、Anthropic、Cursor、Apple 的动作虽然路线不同，但都在强化一个方向：AI 工具必须具备更强的执行能力、上下文治理能力和系统集成能力。
  • 未来的开发者 AI 工具，不再只是插件或聊天框，而更像新的认知执行工作台。
  • 行业竞争的核心护城河，正在从模型分数转移到 harness、权限、记忆、恢复、验证、多代理协作与组织级治理能力。
  • 对企业和创业者来说，真正值得关注的不是“哪个模型今天赢了”，而是“哪套系统开始定义下一代工作流标准”。

第一条信号：OpenAI 正在把 Codex 推向统一开发平台

今天关于 OpenAI 的关键变化，不是又发了一个新名字的模型，而是 Codex 的产品定位变得越来越清晰。

从公开信息看，OpenAI 正在把 Codex 从一个 AI coding assistant，进一步推向更完整的工程协作层：它连接终端、IDE、云环境、GitHub 代码审查，并强化长任务处理、代码审查、自动执行与结果验证能力。

这背后最值得注意的，不是“模型能跑多久”这样的 headline，而是 OpenAI 的方向已经非常明确：

1. 它不想只做一个写代码模型

如果一个产品只强调 benchmark 或补全能力，那它本质还是模型分发层。

但当产品开始覆盖：

  • 本地 CLI
  • IDE 扩展
  • 云端执行环境
  • GitHub PR Review
  • 自动测试与截图验证
  • 跨环境上下文连续性

那它追求的就不是“模型调用量”，而是开发者的主工作流入口。

2. 它在从“回答问题”升级到“接管任务”

OpenAI 对 Codex 的包装，越来越强调长时任务处理、代码审查、复杂重构与工程执行。这意味着行业重心已经进一步远离“问答式编码”，进入“任务委托式编码”。

对开发者来说，区别非常大：

  • 问答式工具，解决的是局部卡点
  • 任务委托式工具，试图接管完整工作单元

这会直接改变开发者工具市场的价值结构。

第二条信号：Claude Code 把 Harness Engineering 推上台前

如果说 OpenAI 今天代表的是“平台收敛”，那 Anthropic 相关话题代表的就是另一件更底层的事情：运行时架构的重要性已经不再是少数工程师的内部认知，而正在成为行业共识。

Claude Code 近期的公开讨论与技术拆解，让更多人第一次系统性地意识到：一个强大的 coding agent 产品，真正的壁垒并不只是模型本身，而是围绕模型搭建的 Harness。

这包括：

  • 控制平面
  • Query Loop
  • 工具与权限
  • 上下文治理
  • 错误恢复
  • 多代理与验证

为什么这件事今天尤其重要？

因为行业正在进入一个阶段：单纯更强的模型，已经不足以解释产品体验差异。

同样级别的大模型，落在不同运行时里，会呈现出完全不同的结果：

  • 有的像会说话的助手
  • 有的像能长期协作的工程搭档
  • 有的像危险但高效的自动化引擎
  • 有的则已经接近可制度化部署的企业级执行系统

这就是 Harness Engineering 的价值所在。它不是优化项，而是 AI Agent 时代的软件工程主轴。

第三条信号：Cursor 在证明“中间层平台”还没有死

Cursor 今天的动作，也很值得重视。

从行业结构看，Cursor 所处的位置最微妙：上游有 OpenAI、Anthropic、Google 这类模型厂商不断下场做第一方工具，下游则是开发者对更直接、更低摩擦体验的需求越来越强。

在这种夹击下，Cursor 的策略非常明确：

  • 用更低价格压缩使用门槛
  • 用更长任务能力强调 agentic coding 价值
  • 用自家工作流与工具栈深度绑定，证明自己不是单纯模型转售层

这背后折射出的行业变化很重要：

1. AI 工具的竞争，已经从“能不能做”进入“值不值得买”

早期用户会追求最强模型，成熟用户则开始关心：

  • 成本是否可接受
  • 长任务是否稳定
  • 工作流是否顺手
  • 团队治理是否完善
  • 产品是否能嵌进日常开发体系

也就是说，行业正在从“能力导向”走向“运营效率导向”。

2. 中间层平台的价值，必须来自运行时与组织能力

未来第三方平台如果还想活得很好，就必须证明自己不只是“替你连了几个模型”，而是能在这些模型之上，提供：

  • 更好的上下文管理
  • 更低的综合成本
  • 更强的团队协作能力
  • 更清晰的审计与权限体系
  • 更符合日常开发节奏的产品体验

谁做不到这一点，迟早会被第一方产品挤压掉。

第四条信号：Apple 正在把 Agent 带进主流开发工作台

Apple 在 Xcode 里更深接入 AI Agent，这不是一条普通集成功能更新，而是一个很强的行业信号。

因为它意味着：agentic coding 正在从前沿实验者的工作习惯，进入主流开发者工具链。

这件事有两层含义。

1. AI Agent 正在成为 IDE 的原生组成部分

过去 AI 工具更像外挂：浏览器里聊天、编辑器里补全、终端里单独跑一个 agent。

但当 Xcode 这种核心 IDE 开始把代理执行、构建、测试、截图验证、检查点回滚整合进开发流程时，AI 就不再是插件，而开始接近原生能力。

2. MCP 这类开放协议的重要性正在抬升

Apple 对 MCP 兼容路径的拥抱，本质上是在承认一件事：未来 AI 工具生态不会只靠单一厂商封闭定义，而需要标准化的上下文与工具连接层。

一旦这个方向继续强化，未来的竞争就不只是“谁有最强模型”，而是：

  • 谁定义工具接入标准
  • 谁定义上下文交换标准
  • 谁定义代理与开发环境之间的默认协议

这类标准一旦形成，带来的长期影响会远比一次模型发布更深。

今天这四条线索，合起来说明了什么

把 OpenAI、Anthropic、Cursor、Apple 这四个方向放在一起看，今天 AI 生态其实已经给出了一个非常清晰的答案：

第一，AI 编程已经从“功能点”变成“基础设施竞争”

它不再只是代码补全、代码生成、PR review 某一个功能，而是在演化成完整开发基础设施的一层。

第二，模型层的重要性仍然存在，但解释力正在下降

未来真正拉开差距的，不会只是基础模型谁领先，而是：

  • 谁的运行时更稳
  • 谁的工具编排更强
  • 谁的记忆系统更好
  • 谁的审批与权限更可信
  • 谁的恢复与验证更成熟
  • 谁更容易被组织级部署

第三，AI 工具行业正在从“新奇体验”走向“制度化交付”

市场最初会为惊艳 demo 买单，但最终会为稳定执行、可审计、可恢复、可协作的系统买单。

这就是今天 AI 生态最关键的变化。

站在行业金字塔视角，我对这轮变化的判断

如果从更长期的产业视角来判断，我会给出几个更明确的结论。

1. 未来一年，AI 工具行业会进一步分层

  • 模型厂商：继续强化第一方 Agent 与基础平台
  • 中间层平台：围绕工作流、团队管理、运行时治理建立护城河
  • 垂直应用层：深入某个明确场景，把 Agent 包成行业解决方案

这三层会同时存在，但价值分配会越来越偏向“谁控制工作流入口”。

2. 开发者工具会继续成为 AI 生态最前沿的试验场

原因很简单：代码、终端、Git、测试、部署，本身就是高度结构化、可回滚、可验证、可观察的环境。相比很多非结构化办公场景，开发者工具天然更适合 Agent 深度渗透。

所以未来很多先进架构设计，仍然会先在 AI 编程领域成熟，然后再外溢到更广的企业工作流。

3. 行业下一轮真正的分水岭，是“可控自治”

不是谁最会说，而是谁最会做；不是谁最像人，而是谁最像一个可靠系统。

这意味着企业最看重的，最终会是：

  • 任务可追踪
  • 行为可审批
  • 错误可恢复
  • 结果可验证
  • 协作可规模化

4. 前沿 AI 工具会越来越像新的操作层

未来最强的 AI 产品，不只是回答问题，也不只是单点执行，而是会长成一层新的认知执行界面：

  • 它理解目标
  • 它连接工具
  • 它管理上下文
  • 它分配代理
  • 它执行任务
  • 它保留审计与恢复能力

谁拿下这层，谁就不只是做了一个 AI 产品，而是在重写知识工作者的默认工作台。

结语

今天的 AI 热点，如果拆开看，像是四家公司各自推进产品路线；但如果合起来看，它们其实共同指向同一个未来：

AI 生态正在从模型时代，走向 Agent 系统时代；从回答时代，走向执行时代；从炫技时代，走向运行时与治理时代。

这就是今天最值得被记录的行业变化。

也是为什么，站在行业金字塔的视角看，今天真正发生的，不是一场普通的 AI 新闻日，而是一轮工作流基础设施重构的加速。

未来的赢家，可能并不是最会发模型的人，而是最先把模型装进可靠系统、可控权限、稳定工作流与组织治理的人。

Claude Code 泄漏事件，真正泄漏给行业的是什么？

By keyed

发表于 2026-04-02

最近 Claude Code 泄漏事件在开发者圈里迅速发酵。表面上看，这像是一场典型的软件发布事故：源代码或相关调试映射文件意外暴露，外界开始围观、拆解、转述、放大。但如果只把它理解成一次“代码被看见了”的新闻，其实低估了这件事的价值。

真正值得行业认真看的，不只是泄漏本身，而是它让外界第一次较完整地看到：一个高能力 AI coding agent 产品，到底是如何被工程化地组织起来的。

对于过去一年一直在做 AI Agent、AI 编程、终端助手、开发者工作流产品的人来说，这件事的重要性甚至不在八卦层面，而在方法论层面。因为它把一个事实彻底摆到了台面上：

下一阶段 AI 工具的核心竞争，不再只是模型能力，而是 Harness Engineering——也就是把不稳定模型约束成稳定系统的工程能力。

导读

很多人以为 AI coding 产品的核心壁垒，是模型够不够强、Prompt 写得够不够巧、界面够不够丝滑。

这些当然重要，但只重要一半。

当模型真正进入终端、文件系统、Shell、Git、权限审批、长上下文、多代理协作这些现实环境之后，真正决定产品上限的，已经不是“它会不会写代码”，而是以下这些更工程化的问题：

  • 它怎么决定什么时候该调用工具
  • 它如何避免危险命令直接落地
  • 它如何管理长会话中的上下文污染
  • 它在失败后能不能恢复，而不是整轮崩掉
  • 它如何把多个代理组织成一个能协作、能隔离、能验证的系统
  • 它如何把这些机制沉淀成团队可持续维护的制度

这整套东西，才是所谓的 Harness。

而 Claude Code 泄漏事件之所以有意义，不是因为“大家看到了 Anthropic 的实现细节”，而是因为行业第一次更清楚地意识到：原来领先的 AI Agent 产品，早就不是单一模型产品，而是完整运行时系统产品。

核心要点

  • Claude Code 泄漏事件最有价值的部分，不是单个功能，而是其背后完整的 agent runtime 思路被外界看见。
  • 这类系统的真正护城河，往往不是 prompt 文案，而是 control plane、query loop、permissions、memory、recovery 与 multi-agent verification 的协同设计。
  • 所谓 Harness Engineering，本质上是在解决“模型天然不稳定，但系统必须稳定”这个矛盾。
  • 未来 AI 编程工具行业的竞争，将从模型能力竞赛，进一步转向运行时架构、权限治理、上下文治理与团队制度化能力的竞争。
  • 对后来者而言，泄漏不是简单复制机会，而是一份路线图：告诉整个行业，Agent 产品必须长成什么样，才可能真正进入生产级。

这次事件泄漏出来的，不只是代码

从公开讨论看，这次外界关注的点非常集中：内存设计、权限系统、工具调用、流式执行、多代理、特性开关、会话持久化、恢复机制等。

如果把这些点拼起来，会得到一个非常清晰的结论：Claude Code 的产品本质，并不是“一个会写代码的聊天机器人”，而是一个被精心包装过的 agent harness runtime。

这意味着，外界真正看到的是一套系统骨架，而不是一堆零散功能：

  1. 控制平面（Control Plane）
    Prompt 不再只是风格设定，而是控制系统边界、预算、工具策略、角色约束与恢复原则的总入口。

  2. 查询循环（Query Loop）
    系统并不是“一问一答”，而是在持续执行“理解任务 → 选择工具 → 获取观察 → 更新状态 → 继续决策”的循环。

  3. 权限系统（Permissions）
    Agent 不能直接接触世界，所有文件写入、命令执行、潜在破坏性行为，都必须被规则与审批机制中断和过滤。

  4. 上下文与记忆治理（Memory Governance）
    长会话下最危险的问题不是“信息不够”，而是“上下文腐烂”。真正成熟的 agent 系统必须知道什么该长期保留、什么只该按需读取、什么必须压缩丢弃。

  5. 错误恢复（Recovery）
    失败不是异常，而是常态。系统设计必须假设模型会走错路、工具会出错、审批会被打断、上下文会失真，所以恢复路径必须是第一等公民。

  6. 多代理与验证（Multi-Agent + Verification）
    当任务规模上升后，一个代理负责所有事情通常不可靠。拆分、隔离、交叉验证，才是把不稳定性关进制度里的方式。

这套骨架，才是 Harness Engineering 真正的主题。

为什么 Prompt 不是核心壁垒，Harness 才是

过去不少团队做 AI Agent，会天然陷入一个误区：把大部分精力放在 prompt engineering 上，以为只要系统提示写得够细，产品效果就能稳定。

这在 demo 阶段常常成立，但在真实工程环境里，远远不够。

原因很简单：Prompt 只负责描述意图，但Harness 决定意图如何被执行。

Prompt 能说“谨慎编辑文件”，但真正防止误删文件的是权限系统；Prompt 能说“保持上下文一致”，但真正避免信息污染的是 memory/index/compact 机制；Prompt 能说“必要时拆分任务”，但真正支持多代理协作的是 worktree、子代理通信与验证层。

所以从产品视角看，Prompt 更像政策文本，Harness 才是宪法落地后的行政系统。

这也是为什么很多 AI 工具看起来都能接同样的大模型，但表现差异极大。不是因为别人多写了几句咒语，而是因为：

  • 它的运行时是否允许低延迟地并发调用工具
  • 它的审批机制是否细粒度且可恢复
  • 它的上下文策略是否能跑长任务而不崩
  • 它的故障路径是否被认真设计过
  • 它的工程抽象是否支持团队级扩展，而不是单人 hack

在这个意义上，Claude Code 泄漏最具启发性的地方，就是它再次验证了一个判断：

AI Agent 产品的真正壁垒，不在模型外面那层 UI，而在模型下面那层 runtime。

Harness Engineering 标准设计，应该包含什么

结合公开泄漏讨论与《Harness Engineering：Claude Code 设计指南》这类材料，可以把一套更标准化的设计框架提炼出来。

1. 控制平面：Prompt 是控制，不是人格

成熟系统的 system prompt 不应该只是“你是一个有帮助的 AI”。

它更像控制平面配置，至少应包含：

  • 角色边界
  • 工具访问规则
  • 预算与成本约束
  • 风险升级条件
  • 上下文写入规范
  • 恢复与中断原则
  • 多代理分工规则

也就是说，Prompt 的目标不是让模型“更像人”，而是让系统“更像一个可管控的程序”。

2. Query Loop：代理系统的心跳

所有 agent 产品最终都要回到一个问题：循环怎么设计。

一个可靠的 Query Loop，至少要解决：

  • 何时继续思考，何时调用工具
  • 工具结果如何进入下一轮上下文
  • 何时触发用户确认
  • 何时触发压缩或摘要
  • 何时重试，何时中止
  • 何时切换到子代理或验证路径

这决定了 agent 是“会说话”，还是“会做事”。

3. 权限与中断：为什么 Agent 不能直接碰世界

任何能写文件、跑命令、访问网络、调用第三方服务的 agent，都必须默认处于受限环境。

标准设计应该至少包括：

  • allow / ask / deny 三层权限策略
  • 对路径、命令、参数级别的细粒度限制
  • 对高风险行为的人工中断
  • 对工具调用结果的可审计记录
  • 对沙箱逃逸或路径穿透的保护

没有这层设计，AI 工具不是 agent，而是事故放大器。

4. 上下文治理：Memory 不是越多越好

很多团队一开始会犯的错误，是把所有历史都塞给模型，觉得“知道越多越聪明”。

实际上长会话下最先崩溃的，往往就是上下文质量。

更好的设计通常是三层：

  • 轻量索引层：永远加载的摘要、目录、关键指针
  • 主题文件层：按需读取的结构化知识块
  • 原始日志层：只做检索，不整体回灌上下文

这不是节省 token 的小技巧，而是系统治理原则。

5. 错误恢复：把失败当成常态来设计

Agent 系统不可能不犯错，所以成熟架构的重点不是“避免所有错误”，而是“错误后仍能继续工作”。

标准设计应包含：

  • 可回滚的文件写入流程
  • 工具失败后的重试策略
  • 会话恢复与断点续跑
  • 审批中断后的重入机制
  • 对不确定结论的显式标注

真正可生产的 Agent，不是从不出错，而是出了错之后不会把整条链路拖死。

6. 多代理与验证：用结构来对冲模型不稳定性

单代理模式在轻任务下足够方便，但一旦进入复杂工程任务，多代理几乎是必经之路。

标准设计往往会包括：

  • 主代理负责任务分解与最终整合
  • 子代理在隔离上下文或隔离工作区中执行子任务
  • 验证代理负责复核关键结论、测试结果或代码改动
  • 代理之间通过明确协议传递观察结果，而不是共享混乱上下文

这本质上是在用工程结构，对冲模型的不确定性。

对 AI 编程工具行业来说，这意味着什么

Claude Code 泄漏事件会带来的行业影响，短期和长期会很不一样。

短期看：认知差被迅速抹平

对很多创业团队和竞品来说，这次事件最大的价值是“看见答案的形状”。

过去大家知道 Claude Code 强，但未必知道它为什么强；现在外界更容易理解：领先产品不是只靠一个模型 API，而是依赖一整套复杂但必要的 runtime 机制。

这会带来一个直接结果：

行业会更快从“做个 AI coding 界面”进化到“做个 agent runtime 平台”。

中期看：产品竞争会转向系统设计竞争

接下来真正拉开差距的，不会只是模型分数，而是：

  • 谁的运行时更稳
  • 谁的上下文治理更强
  • 谁的权限体系更可信
  • 谁的恢复路径更完整
  • 谁的多代理协作更自然
  • 谁更容易被团队制度化部署

换句话说，未来用户买的不只是“智能”，而是“可控的智能”。

长期看：前沿 AI 工具会越来越像操作系统层产品

我对这个行业的一个核心判断是：

未来最强的 AI 工具，不会只是聊天入口，也不会只是 IDE 插件，而会越来越像一层新的软件操作系统。

这层系统不是替代 Linux、macOS 或 Windows，而是长在它们之上的“认知执行层”：

  • 它知道用户当前目标
  • 它知道有哪些工具可以调用
  • 它知道什么可以做、什么必须审批
  • 它知道哪些记忆该常驻、哪些只该按需读取
  • 它知道何时该并发、何时该切换代理、何时该停下来求证

谁先把这层“认知操作系统”做成产品级标准，谁就有机会定义下一代开发者工作台。

我对前沿 AI 工具行业的看法

如果把视角再拉远一点，我对未来两三年的判断大概有五点。

1. 模型会继续进步，但模型差距不再解释全部竞争格局

未来仍然会有模型代际差异，但它们对最终产品体验的解释力会下降。因为越来越多的价值，会转移到运行时、数据接入、权限编排、组织工作流和团队制度化这几层。

2. Harness 会成为 AI 产品经理和工程负责人的核心能力

过去大家讲 prompt engineer，接下来更重要的角色会变成 harness engineer。

会写提示词的人很多，但真正能把模型放进工具、流程、审批、记忆、恢复、多代理系统里，做成可长期运行产品的人，才会真正稀缺。

3. 安全与可控性会从“成本项”变成“销售项”

早期大家会觉得权限、审计、恢复、沙箱这些东西很重，拖慢创新。但一旦 AI 工具真正进入企业与生产环境，用户最愿意为之付费的，恰恰是这些看起来不性感的能力。

4. 开发者工具会率先完成这轮架构升级

因为开发场景天然具备可验证性：有文件、有终端、有测试、有 diff、有 commit。这些都是 Agent 非常适合接管的结构化环境。所以 AI 编程工具会继续成为 Harness Engineering 最先成熟、最先商业化的领域。

5. 下一批头部产品，竞争的是“稳定自治”而不是“惊艳演示”

真正能赢的产品，不一定是第一次试用时最震撼的那个，而是第三十次、第一百次使用时，依然能可靠执行、可被审计、可被团队复用的那个。

这才是生产级 AI 工具的定义。

结语

Claude Code 泄漏事件，表面上是一场产品事故，深层上却像一次行业公开课。

它让更多人看到：顶级 AI Agent 产品的核心，不是一个神奇提示词，也不是一个炫目的模型按钮，而是一整套围绕控制、执行、权限、记忆、恢复与验证构建的运行时工程。

如果说过去一年，AI 行业的主线还是“谁的模型更强”，那么接下来更值得关注的问题会变成：

谁能把模型放进一个真正稳定、可控、可扩展、可协作的系统里。

这，就是 Harness Engineering 的意义。

而这件事，很可能会成为未来前沿 AI 工具行业最核心的分水岭。

从 Polymarket 看 AI 行业预期：预测市场正在如何给模型与产品竞争定价

By keyed

发表于 2026-04-02

过去一年，AI 行业的讨论越来越像一场持续不断的舆论竞赛：新模型发布、排行榜波动、产品更新节奏、融资预期、监管风向，几乎每天都有新的叙事冒出来。问题在于，新闻和社交媒体能放大情绪，却不一定能沉淀有效判断。

这也是为什么 Polymarket 这样的预测市场，开始值得认真看一眼。

在预测市场里，参与者不是单纯表达观点，而是用真金白银对未来事件下注。价格变化本质上是在持续更新一件事：市场认为某个结果发生的概率有多高。当这个机制被放到 AI 行业里，它提供的就不只是热点排序，而是一种对模型竞争、产品能力和产业趋势的“实时定价”。

导读

如果把新闻网站、社交媒体和分析报告放在一起比较，预测市场有一个非常独特的地方：它把“看法”变成了“价格”。

在 Polymarket 这样的市场中，一个事件价格如果是 0.68，通常可以近似理解为市场认为这个结果有 68% 的发生概率。这个价格并不是某个分析师拍脑袋定出来的，也不是一份问卷调查的结果，而是不同参与者在不断交易中形成的平衡点。

这意味着，预测市场天然具备两个特征：

  1. 信息压缩能力更强
    零散新闻、市场情绪、技术更新、产品发布和行业传闻，都会通过交易行为被压缩成一个更简单的数字。

  2. 错误会被资金惩罚
    在社交媒体上，判断错了通常没有代价；在预测市场里，判断错了是会亏钱的。正因为如此，市场价格通常比空泛的观点更值得认真对待。

当然，这不代表预测市场永远正确。但至少在 AI 这种高波动、高噪音、强叙事驱动的行业里，它确实提供了一种更可操作的观察框架。

核心要点

  • Polymarket 上的 AI 相关事件，已经不只是“谁家模型更强”，而是在覆盖模型排名、编程能力、基准测试、监管政策和长期技术里程碑。
  • 在近期 AI 相关盘面中，Anthropic 在“最强模型”这类市场中占据明显优势，说明市场对其模型能力延续性的预期正在走强。
  • 类似“谁会拥有最强 coding model”这样的市场，意味着 AI 产品能力已经开始被直接映射到可交易的概率上。
  • 预测市场并不是真相机器，但它比泛泛的社交讨论更接近一种“带资金约束的行业共识”。
  • 对 AI 产品经理、投资者和行业观察者来说，Polymarket 的价值不在于替代研究，而在于提供一个高频、可量化、持续变化的预期面板。

Polymarket 上的 AI 事件已经在关注什么

很多人以为预测市场只适合政治、体育或者宏观经济，但 Polymarket 的 AI 板块已经比想象中丰富得多。

从目前可见的市场结构来看，AI 相关事件大致分成四类。

1. 模型排名竞争

这是最直观的一类，也是关注度最高的一类。

例如近期关于“哪家公司会在某个时间点拥有最强 AI 模型”的市场，交易量和流动性都不低，说明市场参与者非常愿意对头部模型公司的竞争做出持续判断。当前盘面里，Anthropic 在若干“最强模型”相关事件中处于明显领先位置，这本身就是一个值得注意的信号。

因为它说明市场并不只是认可 Anthropic 某次发布的短期表现，而是在押注其模型优势的持续性。

对于 OpenAI、Google、Anthropic 这类公司来说，预测市场已经不只是“围观榜单”，而是在把它们的技术竞争转化为实时价格。

2. Coding model 与开发者能力

这是我认为最值得产品和投资圈认真看的一个方向。

例如“哪家公司会在 2025 年底拥有最强 coding model”这类市场，背后不是抽象的 AI 概念，而是明确绑定了像 LiveBench coding average 这样的 benchmark 维度。这意味着，市场已经开始把“AI 编程能力”这种产品能力，转化成了一个可以被交易的结果。

这件事很重要，因为过去很多 AI 讨论停留在“能力很强”“体验很好”这种模糊描述上。但一旦进入预测市场，讨论就会被迫具体化：

  • 到底看哪个 benchmark
  • 在什么时间点判定
  • 哪家公司会赢
  • 当前概率是多少

这相当于把“产品竞争”压缩成了一张不断更新的赔率表。

3. 技术里程碑与 benchmark 事件

另一类市场关注的是更长期的技术能力，例如：

  • 某个模型是否会在 FrontierMath 上达到某个分数
  • Chatbot Arena 的分数会不会达到更高区间
  • AI 是否会在数学竞赛层面接近更强的人类水位

这些盘的意义在于，它们不再只是比较公司，而是在给技术进步速度定价。

换句话说，市场不仅在赌“谁更强”，也在赌“AI 技术到底会以多快的速度跨过关键门槛”。

4. 政策与产业层面的事件

AI 相关市场并不只盯模型榜单，还包括：

  • AI safety bill 是否会通过
  • 数据中心政策是否会变化
  • 某些监管事件是否会落地

这说明预测市场已经开始把 AI 当成一个完整产业，而不只是一个技术赛道。模型能力、产品竞争、基础设施和政策环境，正在被一起纳入“未来概率”的框架里。

市场为什么会更偏向 Anthropic

从近期盘面看，Anthropic 在“最强模型”相关市场中的概率显著占优，这背后并不神秘。

第一，市场通常会把最近的基准测试表现和用户评价快速计入价格。如果某家公司在一段时间内持续占据榜单高位，市场会把这种领先解释为更高的延续概率。

第二，市场对 AI 竞争的理解，已经不只是“谁这周发了个新模型”，而是“谁更可能持续把性能、产品化和开发者口碑结合起来”。在这一点上，Anthropic 最近一段时间确实更容易获得“稳定领先”的叙事优势。

第三，赔率本身还受到交易量和流动性的影响。一个有足够流动性的市场，往往能更快吸收新信息，也更容易形成相对稳定的共识。AI 板块里一些高关注事件的交易量已经不低，这让“市场偏向 Anthropic”不只是噪音，而更像是一个可观察的预期信号。

当然，这并不意味着 OpenAI 或 Google 被市场彻底否定。恰恰相反，预测市场的价值就在于，它不是把竞争写死，而是在持续显示：在当前时点，谁被高估，谁被低估，谁还有反转空间。

预测市场对 AI 产品有什么实际价值

如果你是 AI 产品经理、创业者、研究员或者投资人，Polymarket 的价值不在于告诉你“答案”，而在于它能帮助你更快理解预期结构。

对产品经理来说

你可以把它当作一个“外部预期面板”。
市场会告诉你，外界更看重哪些能力：

  • 通用模型能力
  • 编程能力
  • benchmark 表现
  • 产品化能力
  • 长期技术突破

这会帮助你判断，哪些能力是市场真正愿意持续下注的，哪些只是舆论热点。

对投资人和行业观察者来说

预测市场提供了一个比媒体标题更接近资金共识的参考系。
它无法替代尽调，但它能帮助你观察：

  • 哪些方向正在形成强一致预期
  • 哪些事件仍然存在明显分歧
  • 哪些公司正在被市场持续重估

对研究者和开发者来说

像 coding model、benchmark、FrontierMath 这类市场，其实是在提示一个事实：

AI 能力的竞争，正在从“抽象讨论”走向“可量化、可交易、可验证”的阶段。

这对整个行业是一个很重要的信号。

预测市场不是神谕，但它比噪音更有价值

这里也必须泼一盆冷水：预测市场不是神谕。

它有几个天然局限：

  • 会受短期情绪影响
  • 会被流动性约束
  • 会被热门叙事放大
  • 在信息极度不对称时也可能失真

所以正确的用法不是“赔率是多少，我就信多少”，而是：

把它当成一个动态、带资金约束的行业情绪与预期指标。

它比社交媒体更严肃，比单一分析师观点更分散，比普通热点排行更接近真实博弈，但它仍然只是研究框架的一部分。

结语

AI 行业正在进入一个更复杂的阶段。模型能力、开发者工具、产品化节奏、监管信号和资本预期，已经交织在一起。单靠新闻标题和社交平台热度，越来越难判断真正重要的变化。

Polymarket 提供了一种很有意思的视角：当 AI 进入预测市场，它就不再只是一个叙事对象，而开始变成一个被持续定价的现实竞争场。

如果要用一句话总结这篇文章的核心判断，那就是：

预测市场不一定比所有人都聪明，但在 AI 这种高噪音、高变化的赛道里，它正在变成少数值得持续追踪的“概率仪表盘”。

Hugging Face 最新两项观察：从模型碳排放到小模型微调效率

By keyed

导读

Hugging Face 近期连续发布两篇与模型实践密切相关的博客内容，一篇关注 Open LLM Leaderboard 中“模型表现与碳排放”的关系，另一篇则通过案例说明如何借助大模型洞察提升小模型微调效率。两则信息虽然切入点不同，但共同反映出当前 AI 产业的一个清晰趋势：行业竞争已经不再只看“参数规模”和“榜单分数”，而是越来越重视训练与推理成本、工程效率，以及模型在真实业务中的投入产出比。

核心要点

  • 模型性能评估正从单一能力比较，逐步转向“效果、资源消耗与可持续性”并重。
  • 小模型仍然具有现实价值，关键在于如何利用更高阶模型提供的洞察降低微调成本。
  • 对企业和开发者而言，未来更值得关注的不是“最大的模型”，而是“最适合业务场景的模型组合”。

重点内容

1. 模型表现之外，碳排放正在成为新的评估维度

事件概览

Hugging Face 发布《CO₂ Emissions and Models Performance: Insights from the Open LLM Leaderboard》，将公开榜单中的模型性能与碳排放因素放在一起观察。这个角度的价值在于，它提醒行业重新思考一个长期被忽视的问题：当模型能力持续提升时，所带来的能耗与环境成本是否也应成为决策依据。

关键信息

  • 发布主体：Hugging Face
  • 主题归类：性能评估
  • 原始标题：CO₂ Emissions and Models Performance: Insights from the Open LLM Leaderboard
  • 来源链接：https://huggingface.co/blog/leaderboard-emissions-analysis

值得关注的原因

  • 在模型竞赛进入深水区后，单纯追求更高分数的意义正在下降，资源使用效率开始变得更重要。
  • 如果碳排放与性能数据能被更系统地纳入比较框架，将推动行业从“更强”转向“更强且更可持续”。
  • 这类分析也可能影响企业采购、模型选型以及未来对开源模型生态的判断标准。

编辑点评

这篇内容的重要性，不在于它是否立刻改变排行榜本身，而在于它推动了评估逻辑的升级。过去大家更容易关注谁的模型分数更高、推理更快、参数更多；但在商业落地阶段，真正影响决策的往往是综合成本。谁能在可接受的能耗和预算下，提供足够好的效果，谁就更有机会赢得实际应用场景。

2. 借助大模型洞察，重新定义小模型微调的性价比

事件概览

另一篇文章《Investing in Performance: Fine-tune small models with LLM insights - a CFM case study》则把焦点放在“小模型如何借助大模型能力实现更有效的微调”。从标题可以看出，这并不是单纯强调大模型的领先优势，而是试图说明：高能力模型可以作为“指导工具”反哺小模型训练，从而让成本更低的模型在特定任务中取得更实用的结果。

关键信息

  • 发布主体：Hugging Face
  • 主题归类：模型训练
  • 原始标题：Investing in Performance: Fine-tune small models with LLM insights - a CFM case study
  • 来源链接：https://huggingface.co/blog/cfm-case-study

值得关注的原因

  • 这类案例说明，小模型路线并没有失去竞争力，反而可能在企业部署中更具现实价值。
  • 如果大模型能够承担“分析、生成示例、提供反馈”的角色，小模型训练流程就有机会更快、更稳、更便宜。
  • 对预算敏感、强调私有化部署或响应速度的团队来说，这类方法具有很强的可操作性。

编辑点评

行业近两年很容易被“旗舰模型持续变强”这条叙事主导，但真正进入生产环境后，企业经常会回到一个更务实的问题：有没有成本更低、可控性更高、部署更灵活的方案？这篇案例传递出的信号很明确——未来未必是“大模型替代一切”，而更可能是“大模型负责提供智能，小模型负责高效执行”。

结语

综合来看，Hugging Face 这两篇文章分别从“评估标准”和“训练方法”两个方向，回应了 AI 行业当前最现实的两类问题：如何更合理地判断模型价值，以及如何在预算约束下把模型真正用起来。对内容发布和行业观察而言，这类话题比单纯的产品发布更有长期参考意义，因为它们直接触及 AI 进入规模化应用阶段后的核心命题。
